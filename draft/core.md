# OSTF Core: draft contract

Document revision 0.10, 2026-10-22. Wire version `ostf: "0.1"`. This is a working draft, not OSTF 1.0 or a claim of full Core conformance. Requirement IDs below are permanent; retire rather than reuse them. The [support map](support.md) separates this contract, executable coverage and proposed constructs. Historical TRF identifiers refer to the zztrace format from which this draft was extracted; they are informative provenance, not an external normative dependency.

The key words **must**, **should** and **may** are used as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119). They specify this draft, not a regulatory standard. Examples are informative. The text wins over a conflicting schema; such a conflict is a defect. Schemas check serialization shape; semantic validation is also required.

## Boundary and serialization

**OSTF-001: data boundary.** Core describes items, typed relationships, code/test identities, origins and relationship freshness. OSTF specifies the serialized file representation against a source tree; it does not prescribe how a tool stores, indexes or serves the graph internally. Tool commands, search, coverage policy, permissions, approvals, evidence execution, signatures and release decisions are outside Core. A `policy` block is reserved tool data, not an OSTF permission boundary. Corresponds to TRF-001, TRF-004 and the scope's tool boundary.

**OSTF-002: version.** Core root, item and profile files must identify the wire version with `ostf: "0.1"`. The proposed snapshot schema uses the same key for structural review, outside Core conformance. A reader must reject an unknown major or a newer 0.x minor version. Document revisions and conformance-suite versions are independent of that wire version. Future 1.x compatible-minor behavior is outside this 0.1 draft; this draft does not accept 1.0 files. Corresponds to TRF-007.

**OSTF-003: safe YAML.** A document must be UTF-8, contain one YAML document, and use the YAML 1.2 core subset. Duplicate mapping keys, anchors, aliases, merge keys and custom tags must be rejected. Mapping keys must be strings. Booleans are `true` or `false`, rather than YAML 1.1's `yes` or `on`. Dates declared by a profile are strings. YAML parsing precedes JSON Schema validation. Corresponds to TRF-008.

**OSTF-004: files.** The default root is `trace.yaml`. `include` names repository-relative item-file globs; `**` matches zero or more complete path components. Each matched file is read once in deterministic path order, even when patterns overlap. An item file holds the version and `items`, and may hold a document header. Paths must be clean relative slash paths without traversal. Each input file is limited to 8 MiB. For any result, all inputs a reader uses come from one selected source-tree view. An Analyzer's link-state evaluation uses the OSTF files, lock file if present, and referenced source bytes from that view; comparisons between views evaluate each separately. A consumer must report `INCLUDE_EMPTY` when a glob has no unread matches. Version 1's requirements.yaml migration is a zztrace adapter outside this contract. Corresponds to TRF-001, TRF-002 and TRF-006.

**OSTF-005: strictness and extension.** Unknown root/item/profile fields must be rejected unless declared by the selected profile, reserved as tool/module data or prefixed `x-`. An `x-` field is allowed on the Core root, item-file, item, document and profile objects. The proposed snapshot schema also allows it on snapshot files and items; that shape does not add a Core reader obligation. Nested type, link, attribute, provenance and snapshot-header objects do not accept `x-` fields. Readers must retain opaque `x-` values without interpreting them or fingerprinting them. A reader skipping a reserved construct must report `RESERVED_KEY_SKIPPED`. A skipped construct is never evidence that the reader implemented it. Corresponds to TRF-004.

### Evaluation order and diagnostics

Readers establish the graph in this dependency order:

1. Decode each loaded file as UTF-8, parse the safe YAML subset and check its structural shape. A malformed root, profile or included item file stops graph construction; later graph or lock states must not be inferred from it.
2. Resolve the selected profile, then expand and validate includes in deterministic path order.
3. Register items, IDs and aliases. Only registered items may become link endpoints.
4. Resolve item links and validate declared code/test anchor references against the completed namespace and selected profile. An Analyzer additionally binds symbols and enabled tags for its named languages. An invalid link does not enter the usable graph.
5. Check acyclic link types on the usable graph.
6. A Consumer parses `trace.lock` and reports absence, malformed entries and duplicate identities. An Analyzer additionally projects fingerprints and evaluates link states. A malformed lock entry reports `LOCK_INVALID`; other readable entries may still be evaluated. No invalid or unresolved link may be reported valid.

An implementation may collect additional independent errors after an item or link error, but must not report a diagnostic that assumes an invalid prerequisite succeeded. Error ordering and the complete set of secondary errors on multiply invalid inputs are not conformance targets. The fixed conformance cases specify the required codes for their exact inputs.

## Identity, items and profiles

**OSTF-006: identity.** Local IDs match `^[A-Za-z][A-Za-z0-9._-]{0,127}$`. IDs and aliases share a namespace across included files. Names differing only in case must not collide. Aliases preserve nonempty, single-line original identifiers of at most 512 UTF-8 bytes, without surrounding whitespace or control characters; they need not match the ID grammar. Links and tags may resolve aliases; output uses canonical IDs. IDs should not be reused; `obsolete` retires an item. Corresponds to TRF-010, TRF-012 and TRF-013.

**OSTF-007: items.** An item must have an ID, a profile-declared type (default `requirement`), nonempty text unless its type permits omission, and status `draft`, `accepted` (default) or `obsolete`. Optional fields include title, section, rationale, aliases, derived, attributes, provenance, justifications, owners, code and tests. An included file's optional `document` header requires a unique ID and nonempty title and kind; its items retain file order. A derived item must give a rationale. A draft or obsolete item must not satisfy another item's coverage obligation. Coverage evaluation itself is a tool behavior. Corresponds to TRF-020 to TRF-024.

**OSTF-008: profiles.** Without `profile`, the `default` registry applies. A profile file may extend a built-in registry and add types, attributes and link types. Type names match `^[a-z][a-z0-9-]{0,47}$`; link names match `^[a-z][a-z0-9_]{0,47}$`; attribute names match `^[a-zA-Z][a-zA-Z0-9]{0,47}$`. Attributes declare a type, required flag, meaning flag and enum values where applicable. Attribute kinds are string, text, number, bool, date, enum, list of strings and risk-estimate. A date is an exact `YYYY-MM-DD` calendar date string; a list contains strings in written order. Unknown attributes and wrong types are errors. A number is finite IEEE 754 binary64 for canonicalization. Corresponds to TRF-030 to TRF-035.

The default types are `need`, `requirement`, `design`, `risk` and `verification`. Its statements are need, requirement and design. `refines` joins statements and is acyclic; `controls` joins a statement to a risk; `implements` joins code to a statement; `verifies` joins tests or a verification item to a statement or verification item. Inverse names are refined_by, controlled_by, implemented_by and verified_by. Verification has a required `method` attribute: test, inspection, analysis or review; optional procedure and acceptance are non-meaning text attributes. These default attributes have meaning false. The `verifies` role is implementation or effectiveness. The profile's experimental medical extension is not a normative medical-process claim.

## Relationships and identities in code

**OSTF-009: links.** Item links are declared on the source item under their type, as target IDs or objects containing `to` and profile-declared link attributes. Resolve IDs/aliases and validate endpoint types. Reject missing targets, self-links and cycles of an acyclic type; warn about obsolete targets. Compute inverses rather than storing a second edge. `code` and `tests` on an item invert the declaration: the code anchor is the source and the item is the target. Corresponds to TRF-040 to TRF-044.

**OSTF-010: origins.** Core readers report `declared`, `tagged` and `imported` origins separately from freshness. The origin describes how a link entered the graph, not its correctness or when the underlying code was written. `asserted` and `recovered` origins need an accepted recovery record; that contract is deferred outside Core 1.0. Readers must not silently label reconstructed links as approved. Corresponds to the Core part of TRF-045; TRF-046 remains a proposal.

**OSTF-011: anchors and tags.** An anchor is a clean repository-relative path, optionally followed by `#symbol`. Symbol paths and binding follow a named language annex. Whole-file anchors cover the file. `links.source` is yaml (default), both or tags. In both/tags modes, recognize `@req` only inside comments, followed by IDs/aliases separated by spaces, tabs or commas and at most one nonempty `role=effectiveness` or `role=implementation` token. Empty, duplicate and invalid role values report `INVALID_ATTRIBUTE`. Bind to the immediately following documented definition or the innermost enclosing definition; `@req-file` binds to the file. Unknown IDs are `TAG_UNKNOWN_ID`, unbound tags are `TAG_UNBOUND`. Deduplicate a YAML/tag declaration with `LINK_DECLARED_TWICE`. An omitted role remains omitted in lock identity even when interpreted as implementation verification. Corresponds to TRF-050 to TRF-056 and the [Go annex](go.md).

`@req-none`, alternative tag keywords, referenced external identities and recovered-link records are deferred proposals outside Core 1.0. A skipped reserved file key is reported under OSTF-005; permissive parsing does not qualify support for deferred semantics.

**OSTF-012: test identity.** A test anchor uses a runner-defined identity, not a tool-invented display label. The [Go runner annex](go-tests.md) defines the qualified draft cases. JavaScript implementations exist in zztrace, but no normative TS/JS language or runner annex is claimed by this draft. Corresponds to TRF-052 and TRF-070 to TRF-071.

## Meaning and freshness

**OSTF-013: item fingerprint f1.** Project an item to an object with `type`, nonempty normalized `title` and `text`, and a nonempty `attributes` object containing only present attributes declared meaning true. Omit empty strings. Normalize text fields by changing CRLF to LF, removing trailing space/tab/CR on each line, then removing trailing LF. Do not trim leading spaces or normalize Unicode. Include other attribute kinds in their declared JSON type and preserve list order. Exclude ID, status, aliases, section, rationale, links, provenance, owners and extensions. Serialize using [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785), hash the UTF-8 bytes with SHA-256, and encode as `f1:` plus unpadded base64url. Corresponds to TRF-090.

**OSTF-014: code fingerprints.** A language annex defines sig (header) and body (entire definition) token streams. Hash their UTF-8 bytes with SHA-256 and unpadded base64url, prefixed by the algorithm. Whole-file anchors have only sig. For files without a usable token algorithm, `lf1` hashes all file bytes after CRLF-to-LF replacement; the lack of symbol precision must remain visible. [go1](go.md) is the first normative draft algorithm. Corresponds to TRF-091.

**OSTF-015: lock serialization.** `trace.lock` starts with `trace.lock 1`. Each nonempty subsequent line identifies source, link type, target, sorted link attributes and endpoint fingerprints. Its exact grammar and byte escaping are in [trace-lock.ebnf](trace-lock.ebnf). Link identity includes attributes but excludes fingerprints. Duplicate identities are `LOCK_DUPLICATE`, even if hashes differ. Malformed syntax is `LOCK_INVALID`. A writer sorts complete lines. A reader must not silently choose among duplicate stamps. Corresponds to TRF-092.

**OSTF-016: states and precedence.** If no lock file exists, a Consumer reports the absence (`LOCK_MISSING`) rather than inventing per-link states. A Consumer validates the lock grammar and duplicate identities but makes no freshness claim. With a lock, an Analyzer evaluates every current link: broken if an endpoint cannot resolve; otherwise unstamped if its entry is absent (`LINK_UNSTAMPED`) or uses an unknown algorithm (`UNKNOWN_ALGORITHM`); otherwise suspect if OSTF-017 applies; otherwise valid. Broken takes precedence over unstamped, which takes precedence over suspect. Preserve applicable reasons. Returning to stamped content restores valid. Lock-format errors remain errors even if other entries can be evaluated. Corresponds to TRF-094.

**OSTF-017: suspect rules.** A link type's suspect setting counts source, target or both (default). An item hash change on a counted end is `ITEM_CHANGED`; a code sig change is `SIGNATURE_CHANGED`; only if sig is unchanged does a counted body change produce `BODY_CHANGED`. Body changes count for risk-relevant items by default, or all/none under the profile's fingerprints.bodyChange. A non-risk body change can leave a link valid. Impact and executed evidence are separate tool analyses. Corresponds to TRF-034 and TRF-095.

**OSTF-018: risk relevance.** In the default profile, an item with a controls link is a risk control. A control and its refinement descendants, and their linked code/tests, are risk-relevant. This data meaning is in Core because freshness depends on it. The risk may be financial, security or safety related. The medical module's hazard vocabulary remains separate. Corresponds to TRF-064.

**OSTF-019: no assurance inference.** A valid stamp means only that the fingerprinted inputs meet the freshness rules relative to a recorded recheck. It is not approval, correctness, execution, compliance or release authorization. Helpers, constants and dependencies outside an anchor can change without changing that anchor's hash. Corresponds to TRF-091 and TRF-094.

## Proposed areas, schemas and claims

**OSTF-020: referenced items, deferred proposal outside Core 1.0.** External IDs would use `alias:native`; a snapshot would carry read-only data with controlled revision, retrieval and hash provenance. The draft ships a structural snapshot schema for review. Neither current reader implements snapshot resolution or integrity. This ID remains reserved for a separately qualified extension; its schema cases do not create a Core obligation or conformance claim.

**OSTF-021: schema boundary.** Core root, item-file and profile schemas use JSON Schema 2020-12. The proposed snapshot schema uses the same dialect outside Core. Draft schema IDs use `https://ostf.dev/draft/0.1/` as an identifier namespace. A local resolver must not fetch remote schemas during validation. Profile-dependent type/attribute/link checks, YAML safety, graph cycles, clean path and UTF-8 byte limits, hashes and lock states require semantic checks beyond schema shape. The [schema source](../schema/ostf.schema.json) holds shared definitions; entry schemas refer to it. Corresponds to TRF-004, TRF-008 and the scope's schema deliverable.

**OSTF-022: conformance claim.** A Producer writes Core files that satisfy structural and applicable semantic rules for the declared profile; passing JSON Schema alone is insufficient. A Consumer reads every serialized Core construct, resolves IDs and file-declared links, validates lock syntax and reports their origins without claiming source binding or freshness. Where tags are enabled, a Consumer does not present file-declared links as a complete tag-derived graph. An Analyzer additionally binds anchors and tags for at least one named language/runner and computes fingerprints and link states. Deferred constructs do not enter a Core claim merely because their schema accepts them. Claims name document, schema, suite, language and algorithm versions. The current suite is a bounded draft subset, not a full Consumer or Analyzer certification. Independently structured code in the same project is useful cross-implementation evidence, not independent-party review.

**OSTF-023: release gate.** Keep drafts at 0.x. Before 1.0, a second independently maintained implementation must compute its own fingerprints/states and pass the complete conformance suite, and two organizations must use the format on real changes. Neither delegated review nor two projects under one owner proves those adoption gates. Publication of this review draft does not satisfy the independent implementation or adoption gates for 1.0.

## Test traceability

[suite.json](../conformance/suite.json) is the versioned index from these IDs to exact vector/case IDs. The check fails if an executable requirement loses its cases. Proposed or process requirements carry an explicit non-executable disposition instead of a misleading passing test. The text, schemas and annexes are maintained together during this draft; a single-source publication generator remains a 1.0 preparation task.
