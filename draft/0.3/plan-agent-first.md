## 1. Why this plan

The [agent-readiness plan](plan-agent-readiness.md) made OSTF usable by coding agents without growing its core, and its five phases are done. Two independent devil's-advocate reviews of the result, written on 2026-10-25 from the same brief and without sight of each other ([Claude Fable 5.1](reviews/2026-10-25-claude-fable-5-1.md), [Codex gpt-6-astra](reviews/2026-10-25-codex-gpt-6-astra.md)), agree on where it falls short of the intent. That intent is that agents build the traceability and agents use it, for everything that must be linked to code and tests: requirements, risk controls, threat models, design decisions, review procedures and documentation.

The findings, grouped:

- **Defects in the 0.3 text.** Annex K.4 drops line terminators, so two JavaScript functions that differ only by a newline after `return`, and return different values, share a `ts1` fingerprint and produce no impact (found by the Codex review; it follows from the rule as written). Annex I.3 follows item links outward only, so `context R-DATA-AT-REST` on the specification's own example omits `V-ENCRYPTION-REVIEW`. OSTF-144 recognizes risk relevance only through `controls` and `refines`, so a profile link such as the example's `mitigates` to `hazard` never marks code risk-relevant. A lock that is lost or emptied makes a failing repository pass, because `LOCK_MISSING` and `unstamped` do not fail `check`. The grammars the two readers use differ on syntax that, in the decision record's words, "the vectors and fixtures avoid".
- **Evidence gaps.** The trials had no control arm, so they show that agents follow the paragraph, not that the lock, the stamp or the tool improve an outcome over a plain requirements file. The reference reader judged every run. Nothing measures the precision of `suspect`, that is, how often a recheck finds a real mismatch. Round 2 stopped at 86 of 288 runs, paragraph 3 was measured on one small model, and the MCP condition used the shell in about half of its runs.
- **Design limits for agents.** Freshness rests on one human stamp per body change, which cannot keep up with agents that change code continuously, and the stamping agent is usually the one that made the change. One sorted lock per root collides when agents work in parallel. Every language costs an annex with hand-written token rules, vectors and two parsers. The default vocabulary has no threat, control or decision, and the context verb hides verification. The agent paragraph carries workflow policy that OSTF-100 places outside the format. Item text is an injection surface that agents are told to read before every edit.

Both reviews reach a similar verdict: the machinery is reproducible and the discipline is rare; what is unproven is that the freshness machinery produces a review queue worth its upkeep, measured against a plain manifest and Git review. This plan keeps what makes agent-written links trustworthy, replaces attested freshness with derived and corroborated freshness where evidence can replace a stamp, and measures every claim against a baseline.

## 2. Definition of done

> An agent that has never seen OSTF, given the repository and one paragraph, links new code to the requirement, threat, control or decision it serves on the first attempt. A different agent or a person can tell from the repository alone whether that link is corroborated by a test that exercises the code, and when each of its sides last changed. A change by an agent names each item it touched and says whether it still holds, so that the pull request is the review. A repository with a thousand linked symbols and ten agents working in parallel keeps `check` green. Each of these is measured against a baseline that uses no OSTF. Amended under section 8's fallback: the stamp, the recheck provenance and the review queue left the definition with the lock.

## 3. Rules

These bind every phase. A change that breaks one is rejected, however useful.

1. **Core stays at or below 35 numbered requirements.** A new requirement retires or merges an old one. The conformance requirements OSTF-160 to OSTF-162 and the versioning pair OSTF-170 and OSTF-171 are the first merge candidates.
2. **The four-line example stays valid with only its version line changed**, and [fixtures_test.go](fixtures_test.go) keeps enforcing it.
3. **A changed rule is a new identifier, never a silent change** (OSTF-170). `f1`, `go1`, `lf1` and `py1` stay as published unless a defect of the K.4 kind is found in them, in which case the fix is `go2` or `py2`. Amended by the maintainer on 2026-10-25: the wire string stays `ostf: "0.3"` and the lock header `trace.lock 1` through Phase 2, since nobody uses the published draft and the Phase 1 records are the project's own; "0.4" in this plan names the format after Phase 2, not a version string. Fingerprint algorithm identifiers still change with their rules, since the published vectors carry them. Amended again by the maintainer on 2026-10-25, after Phase 3's verdict: under section 8's fallback the fingerprint algorithm identifiers, f1, `go2`, `ts2`, `py1` and `lf1`, are retired with the lock, none replaces them and none is used again, and the vectors published with 0.2 stay as history.
4. **Data, not behavior.** Derivation and triage are defined by the records they write and read, never by how a tool computes them. The record of a derived link says what a test tool observed in which view; the analysis stays outside OSTF.
5. **Policy stays out of the format**, but the diagnostics a policy needs are in it, so a tool can enforce a policy from the result alone.
6. **No claim about agents without a control arm.** Every trial runs a no-OSTF baseline on the same tasks with the same models, and the report gives the difference.
7. **One page per annex**, as before, with one change: a rule that needs room replaces rationale, never another rule.
8. **No agent run before Phase 5.** Added by the maintainer on 2026-10-25, after the baseline. What the Phase 1 records already answer is not run again: Phases 2 and 3 are judged by replaying those records, the trials run again only in Phase 5, and a new model labelling needs the maintainer's approval of its cost.
9. **A missed gate is a cut, not a new mechanism.** Added by the maintainer on 2026-10-25, after Phase 2. When a phase misses its exit gate on the measure written before the measurement, the fallback written beside that gate applies, and no row, default, judge or labelling is added to reach the number another way. Section 8 pre-registers Phase 3's verdict and names its fallback.

## 6. Phase 1: baseline

**Goal.** A number for every scorecard row before any redesign, so that P2 and P3 are judged against it.

**Work.**

- **Control-arm trials of 0.3.** The eight tasks of the [protocol](trials/protocol.md) on both fixtures, in three arms. `none`: the same items in a `REQUIREMENTS.md` with stable IDs and a one-line instruction to read it and run the tests of anything touched, no OSTF files. `intent`: `trace.yaml` and tags with no lock, and a paragraph without the stamping sentences. `full`: 0.3 as published. Two vendors with models matched in size this time, decided by the maintainer on 2026-10-25: Claude Code on `claude-haiku-5-5` and Codex on `gpt-6-sol`, the small model of each vendor, set with the harness's `OSTF_TRIALS_CLAUDE_MODEL` and `OSTF_TRIALS_CODEX_MODEL`; three repetitions. Prose answers are judged by a model that is neither agent, `gpt-6-astra` or `claude-opus-5-5`, the same one for every run, with a human sample of one verdict in ten. The differences between arms are small-model results: a small model gains more from structure and a tool than a large one, so `baseline.md` reports the `full` minus `none` difference as an upper bound for larger models, and the `intent` minus `none` difference, the format without the lock or the tool, as the one that transfers best.
- **Queue precision on real code.** Two repositories the maintainer controls, one Go and one TypeScript or Python, each with at least 200 linked symbols after an agent backfills the links. Replay at least three months of merged history: at each merge compute the suspect links, and have a reviewer, a person or an independent model with a human sample, label each as a real mismatch or noise. Report precision for `BODY_CHANGED`, `SIGNATURE_CHANGED` and `ITEM_CHANGED` separately. This table decides P3's defaults.
- **Parallel-agent fixture.** Ten agents on ten branches of the Go fixture, each changing and restamping distinct functions, merged in sequence. Count lock conflicts and the merges that left `check` red. It runs twice, once with one root and once with the same code split into two roots, so that Phase 2 can tell whether roots alone remove the conflicts or the lock needs sharding.
- **Scale.** Added by the maintainer on 2026-10-25. The target is code bases of about a million lines in which one requirement links many modules and functions, and Phase 2 decides package anchors, sharded locks and the index from these numbers; they measure 0.3 as published and change nothing in the format. One of the two replay repositories is large, with several modules and one root per module, well above the floor of 200 linked symbols, and its replay also reports the fan-out of anchors per item, the lock size per root, the time of `check` and `check --base`, and how many links wanted a package or directory anchor and took a whole-file anchor instead. A generator beside `conformance/generate_tree.py` writes trees whose items link one, ten and a hundred anchors; `check`, `check --base` and `context` are timed on them, and the suspect queue is counted after a synthetic sweep of edits under `bodyChange: all` and `bodyChange: risk`.
- **The first index.** The replay tooling stores each `check` result by view identifier in a small database whose tables are those of the index annex planned in Phase 2. It is the first OSTF index, the longitudinal queries of Phase 5 reuse it, and what it needs from the format feeds the annex.
- **Token cost.** OSTF output read per changed symbol, in every arm.

**Exit gate.** `trials/baseline.md` published with every row of section 2, the differences between arms with intervals, and the precision table.

**Outcome.** Done on 2026-10-25; [trials/baseline.md](trials/baseline.md) gives every row and the [decision record](decisions.md#agent-first-plan-phase-1-baseline) the rulings. Against a plain requirements file, 0.3 helps the small models: task outcome on T1 to T7 was 94 % in `full`, 83 % in `intent` and 60 % in `none`, a difference of 35 points with an interval of 22 to 46, made in asking before changing a risk control, refusing an invented ID and naming the items and tests a change touches. Phase 5 separated the format from its rules on revision 0.16 (section 10): `full` minus `rules`, the same rules on a plain requirements file, was -6 points (-14 to +1), so the format is not shown to improve task outcomes beyond those rules, and what Phase 5 shows for the format is the record, with 96 % of the `implements` links that agents added on tested code corroborated, 0 links broken in 69 merged changes of the longitudinal replay against 2 stale references in `none`, and 107 items that `check --base` listed in those 69 changes, 1.6 a change. `intent` carries the paragraph's rules that `none` lacks, so `intent` minus `none` measures the format together with those rules, and the tool's own share shows on T7, the impact listing, where 1, 4 and 11 of 12 runs named what the change touched. The review queue is where 0.3 falls short. Replayed on three of the maintainer's repositories, 9 % of the labelled `BODY_CHANGED` links and 1 % of the `SIGNATURE_CHANGED` ones were real mismatches, and most `SIGNATURE_CHANGED` came from whole-file anchors and definitions without a body, which `bodyChange: risk` does not quiet. The large repository also broke 548 of its links in three months, which no stamp repairs, and the generated lock of 34 290 links reached 87 % of the 8 MiB limit of OSTF-105, which the reference reader does not apply to the lock. Agents stamped 93 % of the links they touched in the same change, their own changes to risk controls included, as 0.3 asks. The gate holds with three gaps: Breadth is not measured, since its tasks are written in Phase 5; two replay windows are shorter than three months; and an agent, at the maintainer's request, labelled the sample of judge verdicts in place of a person.

**Rulings on the baseline, 2026-10-25.** Nothing that the Phase 1 records already answer is run again (rule 8). The `rules` arm that would separate the format from the paragraph's rules joins Phase 5, which runs the trials again for 0.4 in any case; until then the claim is the one stated above. The records settle the following, and the phases below are amended to carry them: the stamp is replaced for tested code (Phase 3), decided by the precision table and not by a further trial; a whole-file anchor and a definition without a body get reasons of their own, which a profile quiets separately (Phase 2); the lock is sharded, since the conflicts came from adjacent lock lines and a second root changed nothing (Phase 2); links must survive a rename, measured by the new Link churn row (Phase 2); a top-level `check` must name the nested roots it does not cover, and roots must be able to reference each other's items (Phase 2, the diagnostic in the pre-work); the self-stamps of risk controls stand behind Phase 3's separation of duties; `impact.contexts` answers the Tokens row; and a package anchor stays out until the Phase 3 replay still shows the need (section 12). Phase 3's defaults are set by replaying the Phase 1 index and labels under candidate defaults, which costs no agent run.

## 8. Phase 3: freshness per kind

**Goal.** The human stamp is reserved for the links where no evidence can replace it, and the review queue is short and mostly right.

- **Defaults.** The profile's `fingerprints` quiets `FILE_CHANGED` and `DEFINITION_CHANGED` by default, and a profile counts them: the Phase 1 records held no mismatch in 57 whole-file changes and one in 27 changes to definitions without a body, and quieting them halves the large repository's queue; the one lost, a struct whose new fields changed a key, is the price. `bodyChange` stays `all`. `risk` is a profile choice for a repository that has declared its risks, never the default: where nothing controls a risk it equals `none`, and on the backfilled repositories it dropped 18 of the 19 mismatches.
- **Code with tests.** An `implements` link that is `corroborated` in the evaluated view, and whose test anchors are recorded as passed for that view by an Annex E attestation or the tool's own record, is reported with that evidence, and the evidence does not clear it. Every one of the four Phase 1 mismatches on tested code had linked tests that passed in the view where the item no longer held, each a change that added or moved behavior, which an existing test need not catch; exempting tested code would have lost them. Its body change stays in the fingerprint queue and goes to triage like any other, with the evidence as an input.
- **Code without tests.** The fingerprint is the trigger. A recheck is a lock entry whose `by` is not the principal that made the change which caused the suspect state; a stamp by the same principal is `SELF_STAMP`, a warning, and an error under `--strict`. The change's principal comes from the view; in a Git checkout it is the author of the commits between `at` and the evaluated view.
- **Prose to prose.** For `refines`, `controls` and `verifies` between items, the item fingerprints are the trigger and a recheck is a lock entry under the same separation rule.
- **Machine triage.** The fingerprint queue is the list of candidates; the queue a person reads is what triage leaves of it, the links whose verdict is that the item no longer holds or that the triage cannot tell. A tool MAY recheck a suspect link with a model and stamp it as `agent:<model>` when the verdict is that the link holds. ## 12. What stays out, on purpose

- Dependency analysis beyond what a test tool observed. `trace.derived` records observations; `coverage: "direct"` still names the boundary of `impact`.
- Permissions and approvals. Separation of duties is a diagnostic; who may be a second principal is the project's policy.
- A review state on links. The pull request is still the review unit; Git records who wrote a link and when, and, for agents, Agent Trace which session did (Annex G), never that anyone approved it.
- Telemetry and authorship fields. Annexes E and G still point to in-toto and Agent Trace.
- A database as the source of truth. The files in the repository stay authoritative, because a change to code and intent must land in one reviewed commit; an index built from them, for cross-repository and longitudinal queries, is an extension the format is ready for and does not define.
- A package or directory anchor. The Phase 1 replay found a handful of items per root that wanted one, and the whole-file anchors used in its place were the main source of signature noise; Phase 2 quiets those first, and the anchor returns only if the Phase 3 replay still shows the need.
- Any network dependency.

Completing this plan does not make OSTF 1.0. It makes the claim measurable.
