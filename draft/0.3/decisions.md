# OSTF 0.3: decision record

This file keeps the rulings taken while the [agent-readiness plan](plan-agent-readiness.md) was carried out: the ambiguity or defect, the rule that settled it, and the requirement or annex it touched. The plan keeps one paragraph per step and points here; this record keeps the detail, so a reader of a requirement can learn why it reads as it does. Every ruling stayed inside the plan's simplicity budget (plan, section 2): no new Core key, no new requirement, hashes unchanged. Entries are grouped by the step that produced them, in the order the work happened. Where an independent review found the defect, the entry says so; across the four steps below the reviews found 58. The last section records Phase 0 of the [agent-first plan](plan-agent-first.md), which works under that plan's rules (section 3) instead: a changed rule is a new identifier, never a silent change.

## Phase 1: fix the contract

Carried out 2026-10-24 (plan, section 4). Decisions taken while writing Phase 1 that the plan did not spell out:

- **Tag scope.** With tags on by default, a top-level root would also have read the tags of nested roots. OSTF-102 now says a root covers the files beneath it except those beneath a nested root, and OSTF-133 reads tags only there.
- **Result schema.** [schema/result.schema.json](schema/result.schema.json) defines the result format, since three commands now return it. Every result item carries `riskRelevant`. `context` and `stamp` return the same format, restricted, rather than new shapes. One code was added, `STAMP_REFUSED`.
- **SARIF.** Annex D became normative for tools that emit SARIF, because Annex I offers `--format sarif` and a normative annex should not rest on an informative one.
- **Agent paragraph.** F.1 is the only normative part of Annex F. The paragraph is version 1, 190 words, and [fixtures/agent-paragraph.txt](fixtures/agent-paragraph.txt) holds the same bytes, which also delivers the copy-paste file planned for Phase 4.
- **`unstamped` does not fail `check`.** A new link is reviewed in its pull request before anyone stamps it; a team that wants a stricter gate uses a tool option.
- **Independent review.** A second model reviewed the Phase 1 text cold and found 14 defects, all fixed within the budget. The two that mattered most for agents: the paragraph allowed stamping only `suspect` links, so no first lock entry could ever be written, and `context` run from the top level missed a nested root. The others closed determinism gaps: impact on a failed graph or an absent base root, deletions, anchor spellings that bind the same definition, alias versus anchor precedence, which diagnostics a context keeps, unsupported languages in `context`, the origin of a link declared twice, current versus recorded fingerprints, reason order, shell quoting of identities, repeated items in the rendering, and several reasons in SARIF.
- **Expected outputs.** [example/expected/](example/expected/) holds the `check` and `context` results for the refund example, written from the spec text and cross-checked against the lock with the 0.2 prototype's f1 and go1 code. They are the first Phase 2 targets.

Measured on paper: the Annex J rendering of `context refund.go#CheckRefundLimit` is about 130 tokens against the 600 target, and Annex I runs to about 760 words with its table, which fills one dense page and leaves no room: the next rule it needs must replace a sentence.

## Step 2a: the reader

Carried out 2026-10-24 (plan, section 5.1). Writing the port exposed gaps where two readers could disagree, and a second independent review found 17 defects in the reader and in the first round of fixes. All are closed without a new key or requirement:

- Validation is per item and per link instead of stopping the whole file on one bad item (OSTF-150), and the item read later loses a collision (OSTF-110, OSTF-113).
- Names resolve exactly, case included (OSTF-110); undeclared link attributes are rejected (OSTF-134).
- The f1 attribute rules are restated to match 0.2 (OSTF-140). The 0.3 text had silently changed them, which would have broken the rule that hashes never change.
- `PARSE_ERROR` has a defined scope (OSTF-141); lock entries compare key by key (OSTF-144); a broken link stays in the graph (OSTF-151); included files are read as one set in path order (OSTF-102).
- Context results keep lock diagnostics (I.3), result links sort by identity (C.2), and the rendering shows every link from TARGET (Annex J).

## Step 2b: the suite

Carried out 2026-10-24 (plan, section 5.2). The 31 new cases and two direct checks reach what 0.2 never tested, among them external items, tags in a file without an annex, `@req-file`, the 8 MiB limit, path rules, nested roots under an include and the lock file's error handling. Five requirements and three Annex C codes carry a stated reason for having no case, such as the release gate, Consumer-only behavior and `stamp`. The Go tests run the schema cases and check that the schemas accept every root, profile and included file the reader accepts. The second review also found that no case checked an `lf1` value; three cases now do, one with CRLF line ends.

Converting, then two independent reviews, found reader defects in four areas, each fixed with a clarified rule, and eight more unclear rules, all without a new key or requirement:

- The reader used the first of two duplicate lock entries; neither is used now, so the link is unstamped (OSTF-142).
- An include glob read the files of a nested root, whose root keys then stopped the outer graph; includes match only covered files (OSTF-102).
- An unknown profile key gave `UNKNOWN_KEY` at the top level and `PROFILE_INVALID` below it, and a profile that was not a mapping or had no version string gave `FORMAT_INVALID`; every profile schema failure is `PROFILE_INVALID`, after the encoding, size, YAML and version checks that keep their own codes (OSTF-104, OSTF-121, OSTF-150).
- A link attribute named `to` was accepted; `to`, `ref`, `source` and `target` are reserved (OSTF-121).
- The text now says that a malformed first lock line voids every entry (OSTF-142), which codes the item-file rules use (OSTF-102), that every 0.x minor version a reader does not implement is `VERSION_UNSUPPORTED` (OSTF-103), where `x-` keys may appear (OSTF-104), that anchor entries with attributes use `ref` (OSTF-131), that an external item without text keeps its meaning attributes in f1 (OSTF-113), and how Annex C describes `INCLUDE_EMPTY` and undeclared link attributes.

Known reader limits: Go syntax comes from tree-sitter-go plus UTF-8 and escape checks, so some files the Go compiler rejects still parse; reads are not hardened against a tree that changes during a run.

## Step 2c: stamp, impact and SARIF

Carried out 2026-10-24 (plan, section 5.3). The reader keeps its promise of no Git and no subprocess, so `check --base REV` reads the base view from an added option, `--base-tree DIR`, a checkout of REV (Annex I.6), and exits 2 without it; impact cases carry the base view as a second file map. The C.3 example is now computed from the example tree and compared with the JSON printed in the specification, stamping the example's six links from no lock rebuilds its `trace.lock` byte for byte, and the command-line checks run `check --base`, SARIF output, a refused stamp and an accepted one on an edited copy of the example. After every stamp case the suite checks that the named links are valid, no other link changed state and a second stamp changes nothing. `STAMP_REFUSED` now has cases, so it left `notCovered`.

Writing it settled these rules, each a clarification without a new key or requirement:

- **Stamp rewrites the lock as a reader sees it** (I.4). It keeps every entry a reader may use, including entries for links that are not in the current graph, and drops what a reader may not: malformed lines, both entries of a duplicate, and every entry after a malformed first line. So an unnamed link keeps any state it had, and a broken lock line is repaired by stamping rather than by hand (Phase 5, task 8). The first stamp of a repository creates the lock, which gives the other links their first states.
- **A stamp argument names a link byte for byte** (I.2). An alias, another spelling of the anchor or an extra space is `STAMP_REFUSED`, so two tools never stamp different links for the same argument.
- **Stamp diagnostics** (I.4) are `STAMP_REFUSED`, those that stop graph construction, and those of `trace.lock` as read, which name the lines a stamp drops.
- **Impact scope** (C.3). `changed` covers the files that the root covers, or that an anchor of its graph names, in either view: a nested root's code does not show up as unlinked code of the outer root, but an outer link into a nested root's file does. A file that cannot be parsed in a view has no definitions there, so a file that stops parsing lists every definition it had.
- **Test functions** (A.1) are top-level functions of test files named `Test` or `Fuzz`, alone or followed by a character that is not a Unicode lowercase letter, which is the rule `go test` applies. C.3 lists changed ones among the tests to run; methods, helpers, benchmarks and examples are not.
- **SARIF** (Annex D). The rules are the codes and state reasons that the results use, sorted. Every diagnostic subject maps to `logicalLocations`, so a writer need not decide whether a subject is an anchor. A link-state result is located at its source. A `uri` is percent-encoded.
- **Annex I stays on its page.** Four rules were added and five passages of rationale or repetition removed, among them the sentence that `unstamped` does not fail `check`, which the exit-code table already says; Annex I went from 730 to 732 words, table rules not counted.

A mutation pass over the new reader code found one rule no case pinned (impact must not report `PARSE_ERROR` for a file that no anchor or tag needs), and a case was added. An independent review then found nine defects, all confirmed by reproduction and fixed without a new key or requirement; each fix has a check that fails when the fix is reverted:

- **Writes.** `stamp` refused a symbolic link but wrote into a hard-linked `trace.lock`, changing a file outside the root. It now opens the lock without following links and refuses anything but a regular file with one link (I.6).
- **Lost entries.** One lock line that was not UTF-8 voided the whole lock, so a stamp dropped every other entry. Lines are now decoded one by one (OSTF-142).
- **A link that can never stay valid.** A whole-file anchor on `trace.lock` turned suspect as soon as it was stamped. Such an anchor is now `ANCHOR_INVALID` (OSTF-132).
- **SARIF text.** Braces in a message are placeholders in SARIF; they are now doubled (Annex D).
- **The first stamp.** Text `check` printed no identity when no lock existed, so neither a person nor an agent could name a link to stamp first. Links without a state are now listed, as I.2 already required.
- **Paths with `#`.** A file named `a#b_test.go` broke the split between path and symbol, and a tagged file whose name held a backslash crashed `context`. OSTF-105 now forbids `#` in paths and OSTF-102 lets a root cover only files with valid paths.
- **Subtests.** The reader accepted `a.go#F/nope` for any function. Subtest components now bind only to a test function (A.1).
- **Lock values.** The text did not say whether a recorded value such as `go1:bad` makes its line malformed. The 0.2 lock vectors accept such values, so values are compared as written, and `UNKNOWN_ALGORITHM` means a value that does not begin with an implemented algorithm and a colon (OSTF-142, OSTF-143).
- **The state invariant.** I.4 said that no unnamed link changes state, which the first stamp contradicts, and the suite hid it by reading a missing state as `unstamped`. The sentence and the check now compare against the states that an empty lock gives.

A second review of only the fixes found five more, each fixed with a check that fails when the fix is reverted. One was a regression of the first fix: where `O_NOFOLLOW` is missing, as on Windows, the new write path followed a symbolic link, so the explicit refusal is back. "A recorded value" also read as covering link attributes, and now says fingerprint value. The reader refused carriage returns and line feeds in paths, but OSTF-105 did not say so; it does now. The Go schema check kept its own copy of the old coverage rule. `context trace.lock` still bound the reserved anchor, which is now refused where anchors are parsed. These last five fixes were not reviewed again.

## Step 2d: a second reader

Carried out 2026-10-24 (plan, section 5.4). Before any zztrace code, a third independent review read only the five fixes of the second 2c review. Two were right: the fingerprint value wording of OSTF-142 and OSTF-143, and carriage returns and line feeds in paths. Three needed more, each now with a check that fails when it is reverted:

- **Lock writes.** A lock swapped for a link between the reader's check and its write could still redirect the write. `stamp` now writes a new file beside the lock and renames it into place, so a link made in the meantime is replaced, never written through; it still refuses a lock that is a symbolic link, not a regular file or has other hard links. I.6 allows the new file.
- **Include globs in the Go schema check.** `path.Match` read `[x]` as a character class; the check now implements only `*`, `?` and `**` (OSTF-102).
- **The reserved anchor.** On a case-insensitive file system `TRACE.LOCK` is the lock, so OSTF-132 refuses `trace.lock` in any ASCII case; and `context` on an invalid anchor now reports `ANCHOR_INVALID` instead of `UNKNOWN_TARGET` (I.3).

The scoping pass kept zztrace's own model untouched. The second reader is a separate package, `go/ostf`, with the command `zztrace-ostf`; it uses `go/parser` and `go/scanner`, and reads `--base REV` from Git plumbing. zztrace's `trace_*` MCP tools read its own format, not OSTF 0.3, so they cannot be aliases of the 0.3 tools; they stay unchanged in `zztrace-trace`, which is what "kept as aliases" became.

The Go reader was written from the text and passed the shared suite on its first complete run. A differential harness then ran 542 generated edge inputs through both readers and found 285 differences. They came down to a dozen rules the text left open, each now settled in the text with a case, and the reader that read it the other way was fixed:

- **Booleans** (OSTF-101): only `true` and `false`; `True` is a string, as the Python reader had it.
- **Version** (OSTF-103): a value that is not two decimal numbers joined by a dot, such as `"0.3.0"`, fails the schema rather than naming an unsupported version.
- **Codes and types** (OSTF-151, OSTF-131): a value that breaks a rule with its own code gets that code whatever its type, so `id: 123` is `INVALID_ID`, `type: 1` is `UNKNOWN_TYPE` and `profile: 1` and `include: [1]` are `PATH_INVALID`; a link list entry that is neither a string nor a mapping with a string `to` or `ref` is `FORMAT_INVALID`. The existing cases `status-not-a-string` and `attribute-invalid-list` already read the text this way; a first attempt at the opposite rule failed them.
- **Subjects** (C.2): the subject is the first that applies of the unknown name in a tag, the link's source as written, the item concerned, and the line of a tag or of `trace.lock`. It decides which diagnostics a context keeps (I.3), so `context R-F` now shows that R-F refines an unknown ID.
- **Tags** (OSTF-133, A.5, A.2): `@req` must be followed by a space or tab; a definition's lines run from the comments directly above it, each beginning its own line, to its last line, and a tag binds to every definition whose lines include it. A trailing comment therefore binds to its line's definition and never documents the next one, a comment on a grouped declaration's keyword binds to nothing, and each name of `var X, Y` is its own definition, so a tag on it links both.
- **Context** (I.3): two anchors match when they bind to the same definitions, so `a.go#M`, which binds two methods, does not match `a.go#S.M`; an anchor whose file does not exist is `BROKEN_LINK`, whatever its extension; when graph construction fails, nothing resolves.
- **Rendering** (Annex J): a blank text line carries no trailing spaces, as rule 5 already said and the Python reader did not do; the rationale renders like the text, and `external:` joins its parts with commas; links to the same item sort by identity.

Bugs that no rule was needed for: the Go reader removed a cycle's exit link along with the cycle, refused the key `x-` and the `%YAML 1.2` directive, required a nonempty subtest component and reported `UNSUPPORTED_LANGUAGE` for a missing file; the Python reader reported an unknown key in a source entry as `FORMAT_INVALID` and gave link attributes that are not strings the code of the entry. What still differs is the order of diagnostics and the subjects of file-level diagnostics, which C.2 does not compare.

The suite gains 29 cases, one per rule above. Agreement holds case for case and on the generated 10 000-file tree, which [generate_tree.py](conformance/generate_tree.py) writes for both implementations: the same 1 925 links with the same fingerprints and states, the same `impact` after an edit and the same `context` in both formats. `check` on that tree takes 0.19 s in Go and 0.77 s in Python, interpreter start included.

A review of the Go reader against the text, not against the Python reader, found ten defects and one ambiguity in the text. All were reproduced and fixed, each with a case or command-line check that fails when it is reverted:

- **Two rules for the text.** A whole-file anchor spelled like an item ID, such as `a_test.go` next to an item `a_test.go`, gives a link whose identity equals that of a link from the item, so the reader kept whichever it read first; such an anchor is now `ANCHOR_INVALID` (OSTF-132). And YAML 1.1, which both readers' YAML libraries follow here, reads U+0085, U+2028 and U+2029 as line breaks while YAML 1.2 does not, so both readers changed `"a\u0085b"` into `"a b"` and fingerprinted that; OSTF files now exclude the three characters (OSTF-101).
- **Go reader defects.** An unreadable `trace.lock` was reported as missing, so `check` passed; any read failure other than an absent file now exits 2. Tagged links skipped the check of required link attributes. A block comment with CRLF line ends lost its tag, because Go's comment length drops the carriage returns. A `//line` directive moved the lines that tags bind by, which the move to physical lines had already fixed. The bare tag `!` slipped past the YAML subset check, a hexadecimal number above 2 to the 53rd became infinite, an attribute error on an anchor entry named the item instead of the anchor, and `%YAML 1.2` after a comment was refused.
- **Both readers.** `context --root DIR` with a TARGET outside DIR bound the same path inside DIR; such a TARGET now resolves to nothing (I.3). The Python reader also treated a TARGET without `#` as an anchor only when the file existed.

## Phase 3: TypeScript, JavaScript and Python

Carried out 2026-10-24 (plan, section 6). Annex K (`ts1`) and Annex L (`py1`) each fill one page and satisfy OSTF-164; no Core key or requirement was added, and `go1`, `f1` and `lf1` are unchanged.

- **What the annexes follow.** Annex K turns zztrace's existing TypeScript locator into a contract: functions, classes and their members, interfaces, types, enums, namespaces, top-level variables and function assignments, and Vitest and Jest calls with literal names, identified as `Suite > case`. Its tokens are the grammar's, with literals whole, JSX text collapsed and the comma before a closing bracket dropped, which keeps a formatter's trailing commas from changing a fingerprint. Annex L groups Python's tokens into logical lines and records each line's indentation depth relative to the span, so a re-indented method keeps its fingerprint while a statement moved into or out of a block does not; pytest's `::` maps to `.`, and a parametrization identifier in brackets binds the test function as a Go subtest does.
- **Innermost binding.** Classes contain methods and suites contain tests, so a tag binds to the innermost definitions whose lines include it (K.5, L.5); for Go, where definitions do not nest, this is the rule A.5 already states.
- **Two code paths.** The Python reader reads TypeScript and JavaScript with tree-sitter and Python with CPython's own `tokenize` and `ast`; the Go reader reads all three with the grammars that gotreesitter runs in pure Go. The 44 vectors were written by hand from the annex text and pass in both readers. Writing them exposed one rule the text lacked: tree-sitter reads `</` and `/>` in JSX as single tokens, which K.4 now says.
- **Rust stands in.** Six cases used TypeScript or Python as the language without an annex; they now use Rust, and a case checks that `UNSUPPORTED_LANGUAGE` still fires for Rust and Java.
- **Agreement.** Ten cases cover tag binding, test files, parametrization, variables, JSX comments, parse errors, context, impact and stamp in the two languages. A differential run of 81 edge inputs, from abstract classes, overloads, decorators and nested namespaces to f-strings, match statements, continuations and tabs, found no difference in any compared result. The reader's conformance script now needs Python 3.12, whose parser reads the syntax Annex L references.

An independent review of the annexes and both implementations, read against the text, then found 19 defects and 8 places where the text allowed two answers, and the tooling defects listed under Phase 4. Each is fixed or settled with a vector, a case or a converter check:

- **Rules added to the text.** Lines, for tags and definitions, are counted at line feeds (OSTF-133), so a file with bare carriage returns or line separators binds tags the same way in every reader. Annex K now names TypeScript 5.4, spells names as written with a private name's `#`, excludes members named by strings, numbers or computed expressions, takes the same declarations inside namespaces, lets `export` and `declare` combine, treats a parenthesized function as a function, makes template literal types and JSX character references tokens, and requires a test name to be a nonempty single line. Annex L spells names as written, where CPython's parser would normalize them, and binds a parametrized anchor through the member rule of L.2. To stay on its page, Annex K now refers to Annex A for shared rules.
- **Reader defects fixed in both.** Comments inside a template literal produced tags; a comment between a test's arguments, or after a decorator, hid the test or the decorator; `export declare`, destructuring and bracketed member assignments gave no definitions; a Python header's colon could be taken from a decorator's lambda in the body; a Python file with CR line ends was one logical line; and a root directory whose name began with a space lost its Git base view.
- **Known limits.** Both readers read TypeScript with the same tree-sitter grammar, which misses some TypeScript 5.0 syntax, such as `export type *`, and accepts some later syntax, such as `using`; the Go reader's Python grammar likewise accepts syntax after Python 3.12, which the Python reader now refuses. A file using such syntax can get `lf1` in one reader and a token fingerprint in the other; the vectors and fixtures avoid it.

The suite gains 7 TypeScript and 4 Python vectors and 3 cases. The fixes leave every fingerprint of the trial fixtures unchanged.

## Phase 4: remove friction

Carried out 2026-10-24 (plan, section 7). Nothing in the specification changed.

- **One installable tool.** zztrace cannot be installed by others: its module path is not a URL and it depends on a private module. So the reference reader became the installable tool: `pyproject.toml` at the repository root installs it as the `ostf` command, and `pipx install git+https://github.com/ostf-spec/ostf` takes seconds. The agent paragraph's `<tool>` is then `ostf`.
- **`check --base` without a base tree.** The paragraph tells agents to run `check --base <base branch>`, which the reader refused without `--base-tree`. Its command line now reads REV with Git's plumbing commands (`rev-parse`, `ls-tree`, `cat-file`), which run no hooks, filters or repository code, as zztrace's tool does; the reader itself still runs no subprocess. This lifts the limit that step 2c recorded.
- **The GitHub Action and the hook.** `action.yml` installs the tool, runs `check`, prints the impact against a pull request's base branch, uploads SARIF and fails unless `check` exits 0; `.pre-commit-hooks.yaml` runs the same check. The repository's own CI runs the action on the example, on a copy with a suspect link, which must fail with exit code 1, and the hook through `pre-commit try-repo`. GitHub code scanning accepted the uploaded SARIF, the first check of that output by a consumer.
- **Converters.** Doorstop converts both ways; whatever OSTF has no field for travels in `x-doorstop`, so the sample, written and validated with Doorstop 3.2, comes back file for file, and Doorstop validates the exported tree. What is lost is meaning, not data: Doorstop's review stamps are kept but never checked, because OSTF rechecks links with `trace.lock`. StrictDoc imports one way; nodes without a UID and `[TEXT]` nodes are not imported. [tools/README.md](tools/README.md) is the loss report, and CI runs both converters on their samples.
- **The exit gate.** Following the README from an empty repository, with the four-line file, a function and a test, installing from the public URL, checking, stamping, adding the paragraph and the workflow takes about five seconds locally, and the action's job takes about 22 seconds on GitHub. The GitHub side was measured in this repository's CI rather than in a newly created repository.

## Phase 5: measure

Carried out 2026-10-24 (plan, sections 8.1 to 8.3). The [protocol](trials/protocol.md) was frozen before the first scored run and records every later change.

- **Paragraph 2.** In round 1, 18 of the 20 failures were Codex T7 runs that ran the right tests without naming them, because paragraph 1 asked agents to list only what `check --base` reports as added. Paragraph 2 also asks them to name the items and tests that the impact lists. Round 2's T7 runs all passed.
- **Paragraph 3.** In the small-model arm, five of 18 T6 runs created a nonexistent ID that the user had named, as a draft item, under the paragraph's rule that new behavior becomes a new draft item; paragraph 2 never said that such an ID stays invented. Paragraph 3 adds "if the user refers to an ID that does not exist, say so and do not create it", and F.4 says the same. The paragraph grows from 202 to 220 words. Haiku then passed 18 of 18 T6 runs; the larger models did not rerun T6 with it.
- **A third failure category.** Before the small-model arm, the Phase 5 rule gained the model limit: a failure that comes from the model not managing the task changes nothing in the text, so a small model cannot push the paragraph past its budget. It applies to Haiku's four T3 runs that edited a risk control without asking, after `context` had shown it risk-relevant.
- **Two rows lowered.** Find it leaves out T6, because its correct answer needs no tool. Few tokens allows two OSTF calls per changed function or test, counted from the impact of `check --base`, because the paragraph asks for one `context` per function. Both frozen rows stay in every report beside the lowered ones.
- **Harness corrections.** The write detector, once made to ignore quoted text, also hid writes inside Codex's shell wrapper and Python scripts; it was corrected, and every recorded transcript was read again with no pass or fail changing, while the frozen Few tokens row fell from 78 to 73 % in round 1 and from 76 to 65 % in round 2. The judge now compares with the setup commit, because three Haiku runs committed their change. Neither correction changed a recorded pass or fail.
- **Cuts, by the maintainer's choice.** Round 2 ended at 86 of 288 runs, its 24 remaining T7 runs traded for the small-model arm. Round 3 ran T6 on Haiku only after its Sonnet and Codex part was dropped. Haiku was preferred because a text that carries the smallest model is the stricter test, though round 1 showed that a larger model can fail differently.

## Agent-first plan, Phase 0: fix 0.3

Carried out from 2026-10-25 (agent-first plan, section 5). Each change below has a case or vector that fails when it is reverted, and both readers pass it.

- **Line breaks that end a statement** (Annex K.4 and K.6, OSTF-143; found by the Codex review). K.4 dropped line terminators, so `function f() { return` and `1 }` on the next line, which returns `undefined`, had the token stream of `function f() { return 1 }`, and a lock stamped on the second left the first `valid` and out of `impact`. The same erasure merged `a` and `++b` on two lines with `a++` and `b`, `async` alone on a line with `async function`, `break` with `break` and its label, TypeScript's `x` and `!y` with `x!` and `y`, and a type member before a computed member with an indexed access type. The rule is `ts2`: every statement, declaration, class field, member signature and type member that the grammar ends with `;` ends with one `;` token, whether written, left to automatic semicolon insertion or written as `,` after a type member, and an omitted `;` belongs to a span only when the span holds its whole construct, as a written one would. Each merged pair is now a `ts2` vector with two streams. Omitting a `;` that a formatter writes, or writing `,` for it between type members, no longer changes a fingerprint. `ts1` is superseded and keeps its 28 vectors, which both readers still pass; Analyzers implement `ts2` in its place, so a lock entry recorded with `ts1` is `unstamped` with `UNKNOWN_ALGORITHM` until it is restamped. A stream that does not change keeps its digest: 25 of the 28 `ts1` sources write every `;`, and restamping the TypeScript trial fixture changed only the prefix of its 76 code entries. Annex K grew from 727 to 756 words, making room by dropping examples and the list of what its vectors cover. Reading the streams of a token-level differential of 54 inputs, the trial fixture's sources among them, showed that both readers took the keyword `module` for a module declaration without a body, which a vector now pins; after the fix the readers' `ts2` streams agree on every input.
- **The other erased tokens** (Annexes A.3, A.4, A.6, K.4 and L.4). Each annex's dropped tokens were checked for the defect of K.4. Annex K's dropped trailing comma merged `[,]`, an array of length 1, with `[]`, and `[,] = it`, which takes a value from an iterator, with `[] = it`; a `,` before a closing bracket is now dropped only when it does not follow `[` or another `,`, where it is an elision. `ts2` was not yet published, so the exception joins it rather than a `ts3`. `go1` dropped Go's automatically inserted semicolons, and pairs of programs that both compile, as `go build` confirmed, shared a stream: in a function with named results, `return` with `g()` or `<-ch` on the next line returns without calling or receiving, and `x := h` with `(g())` on the next line assigns `h` and calls `g`, where `x := h(g())` assigns the call. `go2` applies the `;` rule of `ts2` to Go's `;`-terminated lists, statements, declarations, specifications, struct fields and interface elements, whether a line end inserts the `;` or a closing bracket lets the source omit it, and A.3 keeps a definition's own `;` outside its span.
